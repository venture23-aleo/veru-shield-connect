STRK20 Messaging · current architecture (direct mode, Sepolia)

How a Message Crosses Sepolia

There is no server, relay, or connection between the two people. The sender encrypts in the browser and writes ciphertext into a contract's permanent storage; the receiver independently computes where to look, reads it back over RPC, and decrypts locally. The blockchain is the only channel.

protected by the channel key — secret visible to everyone on-chain computed locally in the browser

The two halves, step by step

These are sequences — each step feeds the next.

Sending

In the sender's browser, then one transaction

  1. Address the locker. Message #N goes to slot msg_id = Poseidon(STRK20_MSG_ID:V1, ck, N) — random-looking to anyone without the channel key ck.
  2. Derive a one-time key. key_N = Poseidon(STRK20_MSG_KEY:V1, ck, N). Fresh per message; never stored, never sent.
  3. Frame and pad to a fixed tier (256 B / 1 KiB / 4 KiB) so only the size class leaks.
  4. Encrypt + seal with ChaCha20-Poly1305; the slot address is baked into the seal, so ciphertext can't be replayed elsewhere.
  5. Sign and submit one transaction calling privacy_invoke on the helper. The account key's only job — fee 0.2076 STRK for this tier, confirmed in ~10–30 s.

Receiving

In the receiver's browser, every 15 seconds

  1. Compute the same addresses from the shared channel key: slots for N = 0, 1, 2, …
  2. Ask any RPC node which are occupied — one batched slot_lens call covers 16 slots; stop at the first empty one.
  3. Fetch and decrypt locally. Read the felts, derive the same key_N, verify the Poly1305 seal, unframe → sender, time, text.
  4. Rebuildable from zero. A new device with just the keys replays this walk from N = 0 and recovers the whole history — backups hold keys, not messages.

The cryptography

Four primitives, each with one job.

PrimitiveJobWhy this one
Poseidon hash Slot addresses and per-message keys, from channel_key + counter Starknet's native hash — and the same construction the STRK20 pool uses for its own slots, so message slots are indistinguishable from payment slots
ChaCha20-Poly1305 Encrypts the body and seals it against tampering Fast in every browser with no special hardware. The fixed zero nonce is safe only because every message's key is unique — a property the test suite proves
ECDSA (STARK curve) Signs the transaction; pays the fee Standard Starknet account signing. Contributes nothing to secrecy — losing it risks funds, not past messages
Fixed-size padding Hides true message length Observers see a tier, not a length; the compose box warns before a draft crosses into a pricier tier
STARK proofs (Phase B) Will detach the sender's identity from the transaction The message is submitted through the STRK20 privacy pool instead of directly — the one thing today's direct mode doesn't hide

Who sees what

The recipient

  • Everything — text, sender, time
  • With proof it's authentic and untampered (the seal)

A chain observer

  • ~272 opaque numbers stored at a random-looking address, at a time, for a fee
  • In direct mode: the submitting account
  • Never: the text, the recipient, or that it's a “message” at all

Any server of ours

  • Nothing — there is no server

What Phase B changes — and what it doesn't

The seal, the storage, and the receiver's walk stay identical. Only the caller changes.
